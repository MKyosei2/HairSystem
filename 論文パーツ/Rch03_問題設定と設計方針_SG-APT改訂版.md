# 第3章　問題設定と設計方針

## 3.1 対象とする問題

本研究は、ゲームおよび映像制作中のリアルタイムプレビューを想定し、高密度な髪をGPU上でシミュレーションしながら表示する問題を対象とする。評価時の基本構成は、表示髪10万本、ガイドストランド4,000本、フォロワーストランド96,000本、一本当たり128点とする。ガイドストランドの隣接点間を一つのセグメントグループとして扱う場合、物理状態を管理するガイド側のグループ数は50万8,000となる。

画面解像度は1,920×1,080、時間刻みは1/60秒、物理ソルバの反復数は6回を基本条件とする。主対象はGTX 1660級以上のGPUであり、目標は表示、ガイド物理、フォロワー再構築、描画用頂点生成を含む処理全体で安定した60 FPSへ近づけることである。ただし、60 FPSの達成だけをもって提案手法の有効性とはしない。メモリ使用量、GPUバッファの読み書き量、静的再利用の誤差、Fallbackの発生、管理処理の追加負荷も同時に評価する。

本研究が解決しようとする中心的な問題は、すべてのセグメントグループが、毎フレーム同じ量の動的計算用データを必要とするわけではないにもかかわらず、従来の一様なデータ構造では、静的部分にも速度、前フレーム位置、制約計算の一時値などが割り当てられることである。

一本の髪の内部には、次の状態が同時に存在し得る。

- 頭部の移動に合わせて剛体変換だけを行えばよい根元
- 前回の局所形状を再利用できる中間部
- 風や慣性によって動的計算が必要な部分
- 身体や衣服との衝突により修復が必要な部分
- 静的部分と動的部分の境界に誤差が生じた部分

この局所的な違いを利用するため、本研究ではセグメントグループごとに状態を持たせる。ただし、単に物理計算を停止するだけでは、動的計算用データの削減や安全な再利用を十分に説明できない。そこで、セグメントグループを、常に存在する固定コアと、動的状態でのみ有効になる追加Payloadに分ける。

また、本研究は、部分更新が常に有利であるとは仮定しない。衝突や激しい動きによって動的グループが増えた場合、状態判定、一覧生成、Payload管理、Dirty Range生成の追加負荷が、部分更新による削減量を上回る可能性がある。この場合は、SG-APTの通常経路を継続せず、すべてのガイドを通常ソルバで処理するFull Dynamic Fast Pathへ切り替える。

## 3.2 想定する入力と出力

### 3.2.1 静的入力

静的入力は、髪アセットの読み込み時またはトポロジ変更時に設定される情報である。主な入力を以下に示す。

- ガイドストランドおよびフォロワーストランドの点列
- 各セグメントの基準長
- 頭皮または頭部骨格へのRoot Binding
- ガイドとフォロワーの対応関係
- ガイド側のセグメント範囲とフォロワー側の再構築範囲の対応
- 描画用セグメントと描画用頂点範囲の対応
- セグメントグループの親子関係
- 連続するグループをまとめるBlock構成
- Colliderの種類と初期形状
- 物理ソルバの基本設定

各セグメントグループには、実行中に変化しない固定GPUインデックスを割り当てる。このインデックスは、静的状態と動的状態の切替時にも変更しない。

### 3.2.2 フレームごとの入力

フレームごとの入力は、現在のシーン状態によって変化する情報である。

- 現在および前フレームのRoot Transform
- Colliderの位置、姿勢、形状および移動範囲
- 重力、風、加速度などの外力
- ユーザーによる髪の編集範囲
- トポロジ、LOD、Follower Mapping、Solver設定の変更
- フレーム番号と時間刻み
- 静的化および動的化の判定閾値
- Minimum Residence、Hysteresis、Transition Budget
- Full Dynamic Fast Pathの切替に用いるGPU計測値

Root、Collider、外力、トポロジ、編集、依存関係などにはバージョン番号を持たせる。静的Cacheは、必要なバージョンが一致する場合にのみ再利用できる。

### 3.2.3 システム内部で生成する情報

入力から、システムは次の中間情報を生成する。

- 変更が発生したDirty Source
- 変更の影響を受けるBlockおよびセグメントグループの一覧
- 各グループの再利用可能性を表す記述子
- StaticReuse、StaticTransform、Dynamic、Repair、ForcedDynamic、Invalidの状態
- Dynamic Payloadの割り当て一覧と解放待ち一覧
- Dynamic、Static、Repairの各処理対象リスト
- ガイドのDirty Range
- フォロワーのDirty Range
- 描画用頂点のDirty Range
- Full Dynamic Fast Pathを選択するための予測値

### 3.2.4 出力

本システムの主な出力は、次のとおりである。

1. **更新後のガイド形状**  
   動的ソルバ、静的Cache再利用、剛体変換、局所修復の結果を統合したガイドストランドの点列である。

2. **更新後のフォロワー形状**  
   ガイドの変更範囲から依存関係を参照し、必要な部分だけを再構築したフォロワーストランドの点列である。依存関係が不正な場合は、フォロワー全体を再構築する。

3. **描画用データ**  
   変更されたフォロワー範囲に対応する描画用頂点と、Indirect Drawに必要な情報である。変更のない範囲は前フレームのバッファを再利用する。

4. **状態およびPayload管理結果**  
   各グループの状態、動的Payloadのインデックス、Payload Poolの使用量、割り当て回数、Retire回数、Overflowの有無である。

5. **計測データ**  
   GPU Pass別時間、フレーム時間、p95およびp99、動的グループ率、Block Skip率、Payload使用量、GPU読み書き量、静的再利用率、誤静的判定率、境界誤差、Fallback率、Watchdog発火数などである。

## 3.3 要求条件

### 3.3.1 データ構造に関する要求

SG-APTの固定コアは、実行中にGPU上のインデックスを変更してはならない。静的グループは有効なDynamic Payloadを持たず、動的グループは一つだけ有効なDynamic Payloadを持つ。一つのPayloadを複数グループで共有してはならない。

Dynamic Payloadのバージョンが固定コアのバージョンと一致しない場合、そのPayloadを使用してはならない。静的Cacheも、Root、外力、Collider、トポロジ、編集、依存関係などのバージョンが一致する場合にだけ再利用する。NaN、Inf、異常なセグメント長、未解決の共有点、不正なPayload Indexを含むグループを静的状態として扱ってはならない。

Payloadは固定容量のPoolから割り当てる。毎フレーム、グループごとに独立したGPUメモリ確保を行わない。静的化したPayloadは即座に再利用せず、GPU上の参照が終了したことを確認できるEpochまたはFenceまでRetired状態として保持する。Poolが不足した場合は不正なIndexを使用せず、通常のFull Dynamic経路へFallbackする。

### 3.3.2 状態遷移に関する要求

動的状態から静的状態へ移る前に、最終的な動的計算結果を固定コアへ保存しなければならない。静的化は、位置変化、予測変位、制約残差、衝突までの余裕、Root変換量、各バージョンが条件を満たし、その状態が一定フレーム継続した場合にのみ許可する。

反対に、衝突、編集、トポロジ変更、バージョン不一致、境界誤差、異常値など、安全性に関係する条件が発生した場合は、Transition BudgetやMinimum Residenceよりも優先して動的状態へ戻す。

短時間に静的と動的を往復する状態振動を防ぐため、静的化と動的化には異なる閾値を使用するHysteresisを設ける。また、状態変更後は一定期間同じ状態を維持するが、安全上必要な動的化はこの制限を受けない。

### 3.3.3 物理品質に関する要求

動的グループでは、比較対象となる全動的方式と同等の物理ソルバを使用する。時間刻み、反復回数、Compliance、衝突条件、Root条件、数値精度、ソルバ順序を一致させる。提案方式を高速に見せるために、動的グループの物理品質を低下させてはならない。

静的再利用の正しさは、同じ入力条件で全ガイドグループを動的計算した結果を基準として評価する。静的グループの一部には、表示結果へ反映しないShadow Dynamic計算を行い、静的結果との差を測定する。閾値の調整に使用するCalibrationデータと、正式評価に使用するデータを分離し、正式評価前に閾値を固定する。

共有点の最終結果は、GPUスレッドの実行順ではなく、明示した優先順位と誤差に基づいて決定する。これにより、同一入力に対する処理結果と状態遷移の再現性を高める。

### 3.3.4 End-to-End性能に関する要求

ガイド物理だけを部分更新しても、フォロワー全体と描画用頂点全体を毎フレーム更新していては、処理全体の高速化にならない。そのため、ガイドのDirty Rangeをフォロワーの対象範囲へ伝え、さらに描画用頂点範囲へ伝播させる。

変更のないBlockでは、グループ単位の再判定、Payload割り当て、物理ソルバ、フォロワー再構築、描画用頂点生成を省略できることが望ましい。通常実行ではCPUによる全状態のReadbackを行わず、対象リスト、Dispatch数、描画命令をGPU上で生成する。

動的グループ率、Dirty Follower率、Dirty Render Vertex率、各GPU Passの実測時間などから、部分更新経路とFull Dynamic経路の予測時間を比較する。部分更新経路が継続的に不利な場合はFull Dynamic Fast Pathへ切り替え、最適化による負の高速化を抑制する。

### 3.3.5 評価に関する要求

評価では、平均FPSだけでなく、平均フレーム時間、p95、p99、最悪フレーム時間を記録する。また、次の指標を同時に測定する。

- Dynamic Payload使用量
- Payload Allocation数およびRetire数
- グループ関連GPUバッファの読み書き量
- 状態遷移数および状態遷移Byte数
- 静的Cache再利用率
- 誤って静的と判定した割合
- Static/Dynamic境界誤差
- Followerおよび描画のDirty率
- Full Dynamic Fallback率
- Watchdogおよび修復の発火数
- NaN、Inf、不正Index、Pool Overflowの有無

これらにより、SG-APTが単なるSleepingより少ないデータを保持しているか、部分更新による処理削減が画面全体のフレーム時間に反映されているか、精度と安全性を維持できているかを検証する。

## 3.4 現行プロジェクトの課題

本研究開始時点のHairSystemには、10万本の髪を表示する基盤、セグメントグループに関する試作、基本的な状態管理、静的形状再利用の試作、全動的処理の基本経路が存在する。しかし、これらはSG-APTの仕様を満たす一つのデータ型として統合されていない。

第一の課題は、データ構造が固定コアと任意のDynamic Payloadへ完全に分離されていないことである。現行のセグメントグループ情報には試作段階のMetadataが存在するが、静的状態で動的専用データを持たないこと、Payloadの割り当てと遅延解放、バージョン一致による参照可否といった規則が完成していない。

第二の課題は、状態遷移と静的Cacheの有効性判定が不十分であることである。Static Reuseは試作されているが、Root、外力、Collider、トポロジ、編集、Follower依存関係のバージョンと統合された判定が必要である。Root移動も平行移動中心の処理から、回転を含む剛体差分変換へ拡張する必要がある。

第三の課題は、動的グループの物理計算が比較基準と同品質になっていない点である。現行の簡易補正を正式な提案方式のDynamic Solverとして使用すると、性能差がデータ表現によるものか、物理計算の簡略化によるものかを区別できない。そのため、時間刻み、反復回数、制約、衝突条件を全動的Baselineと一致させなければならない。

第四の課題は、共有点の決定性と局所更新の伝播である。共有点処理は部分的な試作にとどまり、候補の生成、優先順位、安定したReduce、最終適用を明確にする必要がある。また、ガイドを部分更新しても、現行経路ではフォロワーを全再構築する処理が中心である。ガイドの変更範囲をフォロワーへ伝える依存関係と、描画用頂点のPersistent Cacheを用いたDirty Range更新が必要である。

第五の課題は、変更の影響範囲を絞る仕組みである。現行のBlock Dirty処理には全体失効が残っている。Root、Collider、外力、編集などの変更範囲をSwept AABBなどで求め、影響を受けるBlockだけを無効化しなければ、50万を超えるグループの判定処理自体が新たな負荷になる。

第六の課題は、部分更新が不利な条件への対応である。Full Dynamicの基本経路は存在するが、動的グループ率だけでなく、GPU Pass別の実測時間、Followerと描画のDirty率、状態遷移数などを用いて経路を選択する仕組みが必要である。

第七の課題は、異常検出と実験証拠の不足である。Watchdogは一部に存在するが、Payload Index、Version、共有点、Follower Cache、Dirty Range、Dispatch数、False Static、GPU Queryなど、提案方式全体を監視する必要がある。Shadow Dynamicも未完成であり、静的再利用の誤差を継続的に確認できない。

また、Pre-Novelty Baselineを収集する実行経路は用意されているが、現時点の開発用結果は、正式な10万本アセットと全シナリオ行列を固定した論文用証拠ではない。したがって、正式評価では、入力アセット、実行環境、閾値、比較条件、計測フレーム数を固定し、BaselineとSG-APTを同一条件で再計測する必要がある。

以上から、現行プロジェクトの課題は、個々の高速化処理が存在しないことではなく、それらが固定インデックスの固定コア、任意のDynamic Payload、Version付き静的Cache、明確な状態遷移、依存範囲伝播、Full Dynamic Fallbackを備えた一つのデータ型として完成していないことにある。本研究では、この不足をSG-APTとして統合し、データ量、GPU帯域、精度、End-to-End処理時間の四つの観点から評価する。
