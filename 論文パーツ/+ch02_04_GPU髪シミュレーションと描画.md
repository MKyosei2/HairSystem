# 2.4 GPU髪シミュレーションと描画

髪は本数が多く、各strandが複数の点やsegmentを持つため、CPUのみで高密度な髪を実時間処理することは難しい。そのため、GPUを用いた髪シミュレーションや描画は、リアルタイムグラフィックスにおいて重要な技術である。GPUでは、多数のstrandや粒子を並列に処理できる一方で、データ依存、共有点の書き込み競合、CPU/GPU間の同期、メモリ帯域などが課題となる。

GPU Gems 2のNalu Demoでは、GPU上で髪アニメーションとレンダリングを行う実装例が示されている[8]。このような実装では、髪の物理処理と描画処理をGPU向けに整理し、複数passに分けて処理することが一般的である。髪の描画では、線、リボン、チューブ、ボリューム的表現などが用いられ、見た目の品質と計算負荷のバランスが求められる。

また、PBDや粒子ベース流体の研究でも、GPU上で多数の粒子や制約を並列処理する考え方が示されている[5][9]。流体、布、髪はいずれも多数の粒子や要素を扱うため、空間探索、衝突判定、制約解決、バッファ更新を複数passで行う構成になりやすい。したがって、GPU上でpassを分割すること自体は既存の実装技術であり、本研究の新規性として主張するものではない。

本研究でも、GPU実装ではStrandCertificateQueryCS、SegmentGroupCertificateQueryCS、StaticCacheReuseCS、DynamicGroupSolveCS、DeferredCorrectionCS、GroupRepairCS、ApplyGroupResultCS、RenderBufferBuildCSなどのpassを想定する。しかし、これらのpassを分けること自体が主張の中心ではない。GPU pass構成は、本研究のデータ構造とruntime decisionを実行するための実装基盤である。

本研究において重要なのは、GPU上でもCPUと同じ処理判断が再現できることである。Segment Groupごとのcertificate判定やstate decisionがCPUとGPUで異なる場合、telemetryの信頼性が低下し、再現実験も困難になる。そのため、本研究ではCPU queryとGPU queryのdecision一致を重要な検証項目とする。

また、group単位で並列処理を行う場合、隣接groupが共有点を書き換える可能性がある。この問題に対して、本研究ではgroup計算中にpoint bufferを直接更新せず、group result bufferへ候補を書き出し、ApplyGroupResult passで反映する方針を取る。この構成により、group単位処理の並列性を確保しつつ、共有点の競合を避けることを目指す。

本研究との差分は、GPU multi-pass実装そのものではなく、Segment Group単位の処理経路選択をGPU上でも実行し、そのdecisionをCPUと一致させ、さらにfalse-static率、Static/Dynamic境界誤差、cache reuse率などをtelemetryとして出力する点にある。GPUは本研究の新規性を支える実装基盤であり、主張の中心はGPU化ではなく、GPU上でも再現可能なcertificate-driven segment-group runtimeにある。
